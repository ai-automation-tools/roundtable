- [x] **The health check calls the web UI healthy while every transcript page 500s** — done 2026-09-11: **(2026-09-11, observed live.)** Three things compose into a failure the automation cannot see. **(1)** `Get-AppProcess` in `scripts/healthcheck-app.ps1` matches a `web_ui.py` process only when its `ExecutablePath` is the **venv** python, so a copy running on a system interpreter is invisible to it — and `startup-app.ps1` skips launching whenever port 8765 already answers, so the stray process holds the port indefinitely. **(2)** The system Python here lacks `linkify-it-py`, which `markdown_it` raises on (`Linkify enabled but not installed`) the moment a message contains a link — so `/conversations/{id}` returns **500** while the app looks up. **(3)** The probe is `GET /` only, and the homepage renders without linkify, so the log says `web UI: OK (HTTP 200)` throughout. Found because the transcript page 500'd after a test launch; every conversation page on this machine was broken and nothing said so. **Fix:** probe a real transcript as well as `/` (the most recent conversation id, or a `/healthz` that renders one), and either detect a foreign-interpreter `web_ui.py` on the port or stop keying process discovery on `ExecutablePath`. Consider failing fast at boot: `web_ui.py` could import what it renders with and exit with a readable message rather than serving a half-working app. **(2026-09-11 closed — and the diagnosis above is PARTLY WRONG; corrected here.)** The symptom was exact: `/` answered 200, every transcript 500'd, the log said `web UI: OK`. Cause (2) was right — the serving process had no `linkify-it-py`, and `gfm-like` enables linkify, which markdown-it-py raises on **at render time**, so a page without URLs renders and one with them does not. Cause (3) was right — the probe was `GET /` alone. **Cause (1) was wrong.** The row blamed `Get-AppProcess` for missing a server started on a "foreign" interpreter. What actually happens on Windows is that **`.venv\Scripts\python.exe` re-execs the base interpreter**: every healthy server runs as a child process whose WMI `ExecutablePath` is `C:\Python312\python.exe`, while inside it `sys.executable`, `sys.prefix` and every import are the venv's. So `ExecutablePath -ieq $Python` did not miss an unusual process — **it could never match the process that serves, on any machine**, and the same test sat in `stop-app.ps1` and `startup-app.ps1`. Caught by testing the fix: a first pass added foreign-interpreter detection that would have flagged and killed every *healthy* server on repair. **What shipped, in three parts.** (a) **The renderer proves itself at import.** `web/render/common.py` renders a URL when it loads and raises with the venv command line if it cannot — a half-working app now refuses to start instead of serving 500s quietly. Verified both ways: the venv boots, a bare `C:\Python312\python.exe` exits with the message. (b) **The probe reads a real transcript**, found by scraping a `/conversations/<id>` link off the list page — no DB access, no new route, sees what a browser sees, and skips itself with a note when there are no conversations yet. (c) **All three lifecycle scripts identify processes by command line**, matching this clone's absolute path — which is what "ours" actually means, and still excludes another clone on the same machine (the reason the interpreter test existed). `start.ps1` is deliberately left alone: it counts sidecar *launchers*, and the ExecutablePath test is what makes it count parents rather than parents plus children. A skipped restart also says so now, naming the PID still holding 8765, instead of logging `restarting` over a launch `startup-app.ps1` declined. **Verified end to end against a stub that answers 200 on `/` and 500 on a transcript**: reported `ERROR` with a non-zero exit where the old check said OK, then `-Repair` stopped it and brought the real server back (both pages 200). Two regression tests: a bare URL must render as a link (`test_web_readonly.py`), and no lifecycle script may match on `ExecutablePath` (`test_availability.py`) — the second checked by reintroducing the old line and watching it fail.

- [x] **🕰️ The sidecar's push watermark ran on the mirror's clock, and skipped local edits forever** — done 2026-09-10: **(2026-08-27)** `sync_once()` in `scripts/db_sync.py` ends every tick with `conversations_updated_after = max(old, max pushed updated_at, server_time)`. The `server_time` term is the anti-ping-pong guard — a row just *pulled* has `updated_at <= server_time`, so folding it in keeps the next push from echoing it back. But it also means the watermark marches forward on the **remote** clock whether or not anything was pushed, so any local write whose `updated_at` lands behind the last tick's `server_time` is never seen by `read_changed_conversations()` — and never will be, because the watermark only grows. Hit for real re-titling #54/#57/#58: three `UPDATE`s with a fresh `updated_at`, watermark already past them, no push logged, mirror unchanged. Recovered with a one-off `--once --state-file` run against a rewound copy of the state. **Two things make it easy to hit:** local and Fly clocks need only differ by a second or two, and two sidecars sharing one `.sync-state.json` (a scheduled one plus a hand-started one) race each other's writes. **The fix is probably to stop mixing clocks in one watermark** — track the pull cursor in server time and the push cursor in local `max(updated_at)` alone, which is what `pulled_updated_at` already does separately. Add a test that writes a row with a stale-but-unsynced `updated_at` and asserts the next tick pushes it. Worth a `--force-push` / `--rewind` flag either way, so recovery doesn't mean hand-building a state file. **(2026-09-10 closed.)** Fixed as proposed: **one clock per watermark.** `run_tick()` advances `conversations_updated_after` / `personas_updated_after` to the highest `updated_at` among the rows it actually pushed — all local values — and the pull cursors keep running on `server_time`, which is where clock-skew protection belongs. The `server_time` term is gone from both push cursors. **The echo the guard suppressed is now paid for openly and is self-terminating:** `/api/ingest` upserts with the row's own `updated_at` and never rewrites it, so a just-pulled row echoes back byte-identical once, and pushing it moves the cursor past it — one wasted POST per hosted-side edit, against a class of bug that silently loses local work. Recovery no longer means hand-building a state file: **`--force-push`** rewinds the three push watermarks for one run and re-ships everything (idempotent by id and composite key), leaving the pull cursors and `known_conversation_ids` intact — deleting `.sync-state.json` threw that list away and with it delete-by-set-difference. New suite **`tests/test_db_sync_watermarks.py`** (9 cases): the headline case stamps a local edit behind a year-2099 `server_time` and asserts the next tick ships it — verified to fail against the pre-fix code — plus the pull cursor still advancing to `server_time`, a hosted delete still propagating, the echo not repeating, and the `--force-push` rewind. Real SQLite seeded through `orchestrator.seeding`; only the two HTTP functions are stubbed. **Not addressed, and still true:** two sidecars sharing one `.sync-state.json` still race each other's writes — a second launcher overwriting the first's state is a separate problem from the clock mixing, and `scripts/start.ps1` already guards against it at launch time.
