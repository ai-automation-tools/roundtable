# Delivery, notifications and the watchdog

> Read before changing `src/orchestrator/delivery.py`, `watchdog.py` or the Notifications / Delivery settings tabs. Moved out of `AGENTS.md` verbatim on 2026-11-22 (audit RT-26) so every agent session doesn't load it; `AGENTS.md` keeps a one-line pointer.

## Delivery (`orchestrator/delivery.py`)

Full reference: [`docs/app/delivery.md`](../app/delivery.md).

- **It renders nothing.** The folder sink writes `export.bundle_files()` verbatim, so a delivered folder is the `.zip` bundle unpacked — **byte for byte**, which is why it writes `write_bytes` and not `write_text` (Windows text mode would turn every LF into CRLF). A format change belongs in `export.py` and its contract doc. `tests/test_delivery.py` compares against the real `render_export_zip()` output, not a fixture. The one non-bundle file, `result.md`, is opt-in for exactly that reason.
- **Off unless `config/delivery.json` exists** — gitignored, same per-machine home as `available-clis.json`. Never ship a default that delivers.
- **`deliver()` must never raise.** Every failure is caught, logged to `logs/delivery.log`, and returned as a string the message path ignores. A sink costs an artifact, never a turn — and one failing sink must not stop the next.
- **Notifications are ONE sink of this, not a second system.** the Settings → Notifications tab + `web/api/notifications.py` render `config/delivery.json` as a form and own exactly the sink tagged `delivery.NOTIFY_SINK_ID`. **Saving merges** — a hand-written folder/command sink survives, which is load-bearing for a gitignored file with no history. Services are a *rendering* (`SERVICES`), never a sink type: `body: "text"` + a templated `template`/`headers` covers ntfy, `text_key` covers Slack/Discord/Gotify, and a per-service adapter for each would be four modules differing by one string. A template's unknown `{placeholder}` renders **empty, never raises** — `quiet_seconds` exists only on `stalled`, and a config that dies on the day it matters is worse than none. `send_test()` deliberately **raises** where `deliver()` swallows; a human is waiting for the answer. `optin_offered()` **excludes** the notify sink by id — it's scoped `"all"`, and counting it makes `/orchestrate`'s *save a copy* box read as forced.
- **`started` is the fourth event and the fourth call site** — `seeding.seed_conversation()`, after the connection closes. It is **not** in the default `events` list on purpose: at seed time the bundle has no messages, so a folder sink inheriting it writes an empty transcript. Pinned by `tests/test_notifications.py`, which seeds for real rather than grepping for the call.
- **Four call sites for the three END paths, and a test pins all three**: `send_message()`, `web.db.stop_conversation()`, `inspect_conversations.cmd_stop()`. Adding another way to end a conversation means adding another `deliver()` call. Do **not** hook `get_my_turn()` — its `maybe_complete()` is only a backstop (the send that ended the run already closed it) — and always call `deliver()` **outside** the write transaction, and only when `complete_conversation()` returned True. **A caller on an event loop uses `deliver_later()`** (a non-daemon thread, events in order): `send_message()`, `web.db.stop_conversation()` and seeding's `started` do, since a sink can take its whole timeout (audit RT-14); the CLI stays inline to print the result. The watchdog counts a stall notified only when `delivery.reached()` finds a line that isn't an `ERROR`.
- **`result` fires per revision, `complete` fires once.** A lead that drafts-then-revises posts several results, so the default `events` list is `complete` alone and the folder sink overwrites rather than appends.
- **Which conversations get delivered is `scope` + `config/delivery-optin.json`, never a column.** A sink is `scope: "all"` (default) or `"opt-in"`; the `/orchestrate` Launch checkbox writes the opt-in list. Do **not** promote it to a `conversations` column — it is a fact about this machine's filesystem, it would have to cross four `SCHEMA` copies plus `db_sync.py` and `/api/ingest`, and it would reach a mirror where `deliveries/` doesn't exist. `tests/test_delivery.py` pins its absence. The `/orchestrate` control has **three** states (off / forced by `scope: all` / live) — don't collapse them, a disabled-but-ticked box is the honest rendering of "every conversation is delivered anyway".
- **The CLI passes `ignore_scope=True`; the automatic hooks don't.** An explicit `deliver <id>` is itself the opt-in. The two operator-stop paths are not — the launch-time decision stands.
- **`watchdog.py` reuses delivery rather than growing a second fan-out.** A stall is a third event (`stalled`) beside `result` and `complete`, so an operator with a webhook already configured needs no new plumbing. It is **read-only and must never touch an agent** — a stalled run needs a human to click something in a CLI window, and ending the conversation would destroy the run it was meant to rescue; a test greps the module for `UPDATE`/`INSERT`/`send_message`/`subprocess`. It notifies **once per stall**, keyed on the last message id so a new message re-arms it. It rides the existing health-check task rather than adding a sixth scheduled job, and its count never feeds that script's exit code.
- The CLI lives in `inspect_conversations deliver`, not in the module: `orchestrator` is a package, so `python -m orchestrator.delivery` cannot resolve from the repo root.
