# The web UI

> Read before changing `src/web_ui.py` or anything under `src/web/`. Moved out of `AGENTS.md` verbatim on 2026-11-22 (audit RT-26) so every agent session doesn't load it; `AGENTS.md` keeps a one-line pointer.

## Web UI (`web_ui.py` + the `src/web/` package)

- Starlette only — `starlette`, `sse-starlette`, `uvicorn`, nothing new. `web_ui.py` is ONLY the entrypoint; implementation goes in the matching `web/` module. Keep route paths defined only in `web_ui.py`, and keep the `web_ui` re-exports (`ReadOnlyMiddleware`, `db_init`, …) working — the tests import them. **Handlers are plain `def`** (Starlette threadpools them; read a body with `web.api.request_json`), so blocking SQLite can't freeze the loop (audit RT-28; details in the `agent-chat-web-ui` skill).
- Binds to `127.0.0.1:8765`. **Do not add a `0.0.0.0` bind without an auth story.** "Reach it from my phone" is already answered without one: `tailscale serve` re-serves the loopback port on the operator's tailnet (`docs/guides/remote-access.md`), and `BasicAuthMiddleware` is the password, **required** once `AGENT_CHAT_ALLOWED_HOSTS` names a non-loopback host on a writable instance (`security.exposure_error()` makes `main()` refuse to start; read from the environment, then `.env`, never `setx`). A wider bind is never the fix for that request. **Every local write needs the per-install write secret** (`WriteSecretMiddleware`, since 2026-11-22, audit RT-05): any GET sets it as the `rt_write` cookie, so a page's own `fetch` carries it, and a test client sends `X-Roundtable-Write: security.write_secret()`. Exempt: `/api/ingest` and the bridge, whose same-origin pass also needs the cookie. **Every `Host` is checked against an allowlist** (`127.0.0.1`, `localhost`, `AGENT_CHAT_ALLOWED_HOSTS`), so a new hosted domain goes into `fly.toml`'s `[env]` before it is attached, and a test client must use `base_url="http://127.0.0.1:8765"` (Starlette's default `testserver` gets 400).
- Write endpoints exist: conversation stop/delete, `POST /api/orchestrate`, the persona endpoints, and `POST /api/ingest` (sidecar sync). A conversation mutation must mirror the SQL the CLI inspector or `orchestrator.seeding` runs; persona writes go through `orchestrator.personas`. Never reimplement seeding SQL or card-writing in a route handler. On the hosted mirror `ReadOnlyMiddleware` + `AGENT_CHAT_PUBLIC_READONLY` 403s browser mutations, so add a case to `tests/test_web_readonly.py` for each new write route.
- **The hosted demo strip and `ReadOnlyMiddleware` key off the same flag** (`_is_public_readonly()`), so a page promising "read-only" and a server allowing writes can't come apart. Not dismissible, not gated on anything else.
- **`/personas` is the read-only explorer; the management console is `/personas/manage`** (since 2026-11-06, when the AI-Automation-Library's static Persona Registry was retired into this app). The explorer must stay GET-only so the hosted demo serves all of it, and its `.zip` download must keep re-importing through `/api/personas/import` (pinned by `tests/test_persona_explorer.py`). Covers come from `PERSONA_MEDIA_URL` and always fall back to the avatar. The rail's *Personas* row opens the **console**; the explorer is a **standalone site**, `personas.ai-automation-tools.dev` (a Fly cert on the mirror), with its own chrome (`_registry_layout`, no rail). On that host `RegistryHostMiddleware` serves only the explorer and bounces every other path to the demo. The app links **out** to it (the *Persona registry* rail row, the console, the home page); don't render it inside the app shell.
- **Personas are DB-backed, so persona management is NOT local-only** — `/personas/manage` works on the hosted mirror too. `personas.root_exists()` returns True whenever the DB is reachable; the failure it guards is "database unreachable" (404 + `persona storage unavailable`), not "no local cards". The `agents/Debate-Agents/` card tree is only a one-time seed source for `import_personas_from_files()`.
- **SSE is one channel:** `event: message` per row, `event: turn` on a `current_turn` change, `event: complete` on close. Reuse it rather than opening a second.
- **Per-machine config is ONE page.** `/settings` has three server-side tabs (`?tab=clis|notifications|delivery`) over the three things in `config/`. Tabs are **links, not JS** — only the selected tab's markup and script reach the page, so three forms written months apart can never collide on an element id and the HTML-string tests keep working. `/setup` and `/notifications` **302** to their tabs (`settings.LEGACY_PATHS`, pinned by a test) because they are linked from the README, the docs tree and bookmarks. A new setting is a tab entry plus a body builder; **a secret, a deployment posture or a launch argument is not a setting** and stays in the environment — see `docs/app/settings.md` for the line.
- **The Delivery tab owns sinks BY POSITION, the Notifications tab by ID.** Folder and command sinks predate any UI and carry no `id`, so `api/delivery_settings.py` edits the *first* of each type in place, preserves keys the form doesn't know, and reports later ones in `extra_sinks` rather than touching them. Tagging them on save would silently rewrite hand-written configs — the one thing a form over a gitignored, history-less file must not do. It never touches the webhook sink; two pages writing one sink is how that file loses work.
- **The nav rail is two tables:** `_NAV_ITEMS` = pages this server renders; `_RESOURCE_NAV_ITEMS` = reference + third-party destinations under a separator. Don't collapse them — one column made an external link read as a page of this app.
- **Never assume the operator has every CLI.** `/orchestrate` and the homepage read `orchestrator.availability`, not `preflight.discover_seats()`. Availability is advisory — `POST /api/orchestrate` still gates on preflight. Detection names must stay in sync with `$Clis[...].Exe` in `scripts/lib/spawn-agents.ps1` (pinned by `tests/test_availability.py`).
- **`/orchestrate` must seed through `orchestrator.seeding.seed_conversation()`** — the same function `start_conversation.py` calls.
- **A seat is created by cloning seat 1's config — from one of THREE places.** `add_agent_seat._seat_one_config_text()` tries `CliShape.source_override` (an explicit global path — Codex's `~/.codex/config.toml`), then the seat-1 folder, then `CliShape.user_scope_entry` (a callable returning the tool's user-scope `roundtable` entry, from which a minimal config is **synthesized**). The third exists because Claude Code's seat 1 is *expected* to have no project `.mcp.json` — one there makes it prompt for approval on every launch and stall a spawned agent — so cloning a file that must not exist made a second Claude Code seat impossible on every machine. A new CLI that registers globally must declare one of the two fallbacks; `tests/test_seats.py` pins the set against preflight's. Only the `roundtable` entry is carried across, never the rest of `~/.claude.json`.
- **The form picks TOOLS; seat ids are derived.** `/orchestrate`'s Participants section is one row per **chair** — a dropdown of this machine's CLIs, that chair's persona, its custom-card button, a remove button — not a checkbox per seat id. The seat number comes from chair order (`renderSeatIds()` / `roomSeats()` in `web/render/orchestrate.py`): the second chair on a tool is `claude-code-2`, shown read-only in the row. So **the host may run on the same tool as a guest** — it just takes its own seat number — and a one-CLI operator can fill a whole room. `POST /api/orchestrate` creates any missing seat folder **before preflight**, through `web.api.setup._add_seat_module().add_seat()` — never a second copy of that logic. Consequences: nothing may re-introduce a control that picks a seat *id*, personas are a column of the chair row (there is no separate Personas section to keep in sync), and the per-tool ceiling is `seats.MAX_SEATS_PER_CLI`, enforced in the form before submit **and** by `seats.seat_id()` on the server.
- **Nothing *runs* the form's JS.** `tests/` asserts on rendered HTML strings, so a selector that hides the right markup passes every suite — that is exactly how the host seat picker shipped invisible (`updatePersonaRows()` caught the moderator's rows too). `tests/test_orchestrate_form.py` now pins the string invariants a browser would make redundant — every id / `[name=…]` / `.class` the script looks up resolves against the page, no bulk query runs at document scope, and a bulk-hidden class stays inside the container that owns it (`_BULK_HIDDEN_CLASSES`) — and since 2026-10-29 `tests/test_orchestrate_browser.py` runs the script in a real headless Chromium for the chair engine's core behaviour (derived seat ids, the visible host picker, the per-tool cap, format clamping, the custom-card POST). That suite needs Playwright, which is **CI-only** (`requirements-dev.txt`, never `requirements.txt`) and **skips cleanly** without it — so a local run on the bare venv still executes none of the JS. Everything else the script does (presets, extra seats, the recap, spawn/delivery toggles) is unexercised. Say so when reporting work on `web/render/orchestrate.py`, and re-check the page in a browser rather than trusting a green run.
- **Export rendering lives in `orchestrator/export.py` and its output is a contract.** `/export.md`, `/export.zip`, and the delivery folder sink all render through it, and whatever reads those files parses the format: heading shapes, meta-table labels, `## sender — timestamp` headings, persona filenames, and the 25-char `topic_slug` are effectively frozen — read `docs/app/export-format.md` first.
- **Topic logos** are classified at render time by `web/topics.py` — no schema, no backfill, so re-wording the `TOPICS` table re-skins the whole archive. Ties go to the earlier entry, which is why `ai` sits near the bottom.
- **Persona avatars** resolve at render time from the persona **slug** (`web/avatars.py`, served at `GET /avatars/{slug}`): an uploaded image on the DB row → `images/AgentChat-Avatars/<slug>-avatar.png|svg` → `default-avatar.svg`.
  - **Uploads belong in the DB, never on disk** — the `personas` table syncs to the mirror with no redeploy and survives the next one; a file wouldn't.
  - **Uploads are raster-only, typed by magic bytes** (`normalize_avatar`), never by declared MIME. **SVG is refused** (script-capable markup on the app's own origin); stored bytes ship with `nosniff` + `default-src 'none'`.
  - **An avatar must survive an edit:** `update_persona()` touches it only when passed `avatar=`/`clear_avatar=`, and both import paths carry the image across an overwrite.
  - `list_personas()` selects an explicit column list **excluding `avatar_data`** — `SELECT *` would haul every image through every roster render.
  - Shipped file art needs a commit + Fly redeploy (the folder is COPYed into the image). No-persona conversations resolve from the raw agent id, which for a CLI *is* its brand-avatar slug.
